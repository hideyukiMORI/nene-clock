# 開発ワークフロー — NeNe Clock

> Status: normative（規範）/ 2026-09-03 初版 / 2026-09-22 第 9 節（検証の選び方）を追加

ワークフローは制約系の一部である。**追跡可能な手順の外で作られた技術的に正しいパッチは、未完成である。**

---

## 1. 作業の単位

production コード・ビルド・依存・方針・利用者向けドキュメントの変更は、
すべて 1 つの焦点を持つ Issue から始める。Issue には次を書く。

- 問題と根拠
- 意図する結果
- 影響する規則 ID とモジュール
- 受け入れ条件
- 検証の計画
- **やらないこと**

読み取りだけで、リポジトリを変更しない調査は Issue 無しで行ってよい。

---

## 2. 標準の流れ

1. 焦点を持つ Issue を 1 つ作る／選ぶ
2. 正本のドキュメントと関係する ADR・waiver を読む
3. **編集の前に**正典の実装経路を特定する
4. 最新の `main` からブランチを切る
5. 設計そのものを変えるなら、**先に**方針文書か ADR を変える
6. 最小で完結する変更を実装する
7. テストを足す／更新する
8. **差分から検証を選んで回す**（何を変えたら何を回すかは第 9 節）
9. 引き渡し前の全件 `./gradlew check` は**最大 1 回**。差分が Gradle の入力に触っていなければ回さない
   （完了の判定は CI の `quality` ジョブが 1 回行う）
10. 影響した規則 ID を 1 つずつ自己レビューする
11. Issue に紐づけて PR を出す
12. 必須ゲートが通ってから merge する
13. ローカルの `main` を同期して綺麗な状態に戻す

---

## 3. ブランチとコミット

ブランチ名:

```text
<type>/<issue番号>-<short-kebab-summary>
```

コミット（Conventional Commits）:

```text
<type>(<scope>): <日本語の説明> (#<issue番号>)
```

`type` は `feat` / `fix` / `docs` / `refactor` / `test` / `build` / `ci` / `chore`。
`type` と `scope` は英語、説明は日本語。
1 つの PR にアーキテクチャ移行・無関係な整理・依存更新・機能追加を混ぜない。

---

## 4. 決定の記録（ADR）

### ADR が要るもの

- 憲章規則・依存方向の変更
- モジュール境界・状態の所有者の変更
- 公開 API の変更
- 保存形式の方針
- 合成／DI の方針
- 並行性・スレッドモデル
- 整形器・静的解析器・テスト枠組み・主要な Gradle プラグインの変更
- 対応プラットフォームの変更
- 品質ゲートの重大度・閾値・除外の変更（QLT-010）

### ADR が要らないもの

- 承認済みの境界の内側に閉じた実装の詳細
- 文書化された振る舞いを回復するだけの不具合修正
- 方針を変えないテストとドキュメント
- 契約に影響しない小さな依存更新

---

## 5. 規則を変える手順

MUST / MUST NOT を変えるには次がそろう必要がある。

1. 矛盾と根拠を書いた Issue
2. 受理された ADR
3. 正本ドキュメントの更新
4. 強制（ゲート）の更新
5. コードの移行
6. **旧経路が拒否されることを示す回帰テスト**

これらは同時に入るのが原則である。段階移行が避けられないときは、
期限付きの waiver を作って二重状態を明示する。

---

## 6. 依存の方針

新しい実行時依存を受け入れるのは、次がすべて満たされるときだけである。

- その機能が具体的にいま必要である
- 自前で書くほうが危険か、保守しにくい
- ライセンスと保守状況が受け入れられる
- 正しい境界の裏に隔離できる
- 版が固定でき再現可能である（QLT-011）
- 必要なら ADR がある

**便利だから、は理由にならない。** 0.1 系では JDK 以外の実行時依存を持たない方針である
（テストと検査の依存は別）。

---

## 7. PR に書くこと

```text
Issue:
目的:
使った正典経路:
規則 ID:
振る舞い・スキーマの変更:
検証（実行したコマンドと結果・検証済みの木 `git rev-parse HEAD^{tree}`・回さなかった検査とその理由）:
Waivers: none | WVR-NNNN
残るリスク:
```

レビューは次を拒否する。

- 既存の意味に対する第 2 の経路
- 所有者の書かれていない状態
- 弱められた／飛ばされたゲート
- 範囲の広い抑制
- アダプタ固有の業務ロジック
- 「将来使うかもしれない」公開 API
- 機能変更に紛れ込んだ無関係な整理

---

## 8. ドキュメントの方針

重要な決定を、チャット・Issue のコメント・コミットメッセージ・AI との会話ログだけに残さない。

- 長生きする不変条件 → 正本ドキュメント
- 判断とトレードオフ → ADR
- 一時的な逸脱 → waiver
- いまのタスク状態 → Issue / PR
- コードのコメント → その場の非自明な理由（方針そのものは書かない）

設定ファイルとドキュメントが食い違ったら、**ドキュメントが決定の記録**である。
ただし両方がそろうまで merge は止める。

---

## 9. 検証の選び方 — 差分から選ぶ

> 2026-09-22 追加（Issue #92 / [ADR 0016](adr/0016-verification-is-selected-from-the-diff.md)）。
> 第 2 節の手順 8・9 はこの節に従う。規則としての定義は QLT-013。

完了の定義は `./gradlew check` **1 本のまま**である（QLT-001）。
この節が決めるのは **その 1 本をいつ回すか**と、**開発中は何を回すか**である。

### 9.1 原則

1. **説明できない検査は回さない。**「この変更で何が壊れうるか」を言えないなら、その検査は選ばない
2. **成功は再利用する。** 同じ木に対する成功した検証を、担当・工程・文書追記・コミット ID の
   変更だけを理由に回し直さない
3. **全件は既定ではない。** 回すときは対象と理由を 1 行書いてから回す
4. **無関係な失敗で止まらない。** 差分に起因しない既存の失敗は、根拠とともに別 Issue にする
5. **緑になるまで回さない。** 再実行で通ったことを合格として扱わない（不安定なテストはそう報告する）

### 9.2 何を変えたら、何を回すか

| 変えたもの | 回すもの | 回さないもの（理由） |
| --- | --- | --- |
| 文書（`*.md`）・コード内のコメント・PR 本文・日報・引き継ぎ書 | 規則 ID・waiver・モジュールグラフの記述に触れたなら `./gradlew validateConformance`（CNF-005 / CNF-009 / CNF-010）。触れていないなら**何も回さない** | 単体テスト・ArchUnit・全件。Java とビルドの入力が 1 バイトも変わっていない |
| `:core:domain` の振る舞い | `:core:domain:test` ＋ 直接の呼び出し元 `:core:application:test` | UI・アダプタのテスト（依存は core へ向かうだけで、逆は無い — ARC-002） |
| `:core:application` の振る舞い・ポートの契約 | `:core:application:test`。**ポートの署名や契約を変えたなら**その実装アダプタの `test` も | `:core:domain:test`（下位は変わっていない） |
| `:adapters:*` の実装 | そのアダプタの `test` だけ（例: `:adapters:preferences:test`）。保存形式を変えたなら移行のテストを必ず含める | 他のアダプタ（互いに依存しない） |
| `:ui:swing` の描画・レイアウト・文言 | `:ui:swing:test` ＋ 🔴 **`./gradlew run` で目視**し、見たものを [quality/gate-proofs.md](quality/gate-proofs.md) に記録する（QLT-012） | 他モジュールのテスト。⚠️ **`check` の緑は見た目について何も言わない**（2026-09-04 に 4 件の見落とし） |
| `:app`（合成ルート）・起動経路 | `:app:test` ＋ `./gradlew run` で起動確認 | core のテスト |
| 同梱書体の追加・差し替え | `:adapters:font-catalog:test`（存在・SHA-256・Regular で描けるか）＋ `:ui:swing:test`（`:ui:swing` は **testImplementation で font-catalog に依存**している。production の依存グラフには現れない辺である） | 他すべて |
| `build-logic` の規約検査 | `:build-logic:test`（正例・反例 — QLT-007）＋ `./gradlew validateConformance` | アプリのテスト |
| モジュール境界・依存方向・例外区画・`config/forbiddenapis/*` | `:quality:architecture-tests:test` ＋ `./gradlew validateConformance` | |
| 共通基盤（`build.gradle.kts` / `settings.gradle.kts` / `gradle.properties` / `build-logic` の規約プラグイン / `config/` / 整形設定 / JDK / 依存 lock） | **全件 `./gradlew check`** — これが「限定した検査では影響を確認できない具体的な理由」の例である | |

表に無いものを変えたときは、**影響先を 1 つずつ挙げてから**選ぶ。挙げられないなら、それは
「共通基盤を触った」ということなので全件を回す。

### 9.3 成功の再利用 — 鍵は木のハッシュ

```bash
git rev-parse HEAD^{tree}   # 検証した内容の同一性。コミット ID ではなく、これで比べる
```

**木が同じなら結果は同じ**である。rebase・amend・squash・メッセージの書き直し・担当の交代・
レビューの往復・merge は、いずれも木を変えない限り再実行の理由にならない。

回し直すのは次の 3 つのいずれかのときだけである。

1. 木が変わった（しかも変わった部分が、その検査の入力である）
2. 前回落ちた
3. 具体的な未確認事項が残っている（「何が未確認か」を言葉にできること）

PR 本文の「検証」欄には、**回したコマンド・結果・検証済みの木のハッシュ**を書く。
回さなかった検査があるなら、なぜ不要かを 1 行で書く。

### 9.4 自動実行の分担（人が手で重ねない）

| 誰が | 何を | 位置づけ |
| --- | --- | --- |
| CI `quality`（`pull_request`） | `./gradlew check` | 🔴 **これが完了の判定**。1 PR につきこれが正本 |
| CI `quality`（`push: main`） | 同じ `./gradlew check`。ただし `paths-ignore` で `**/*.md` / `docs/**` / `LICENSE` だけの merge では回さない | **ゲートではない**。merge 後の `main` を緑に保ち、次の PR のためにビルドキャッシュを温める（実測: キャッシュが効いた CI は 39〜101s、冷えると 217〜258s）。だから消さず、**内容が同じになる merge でだけ止める**。⚠️ これを理由に手元で全件を回さない |
| CI `Release` | `packageInstaller` のみ | 配布物を作るだけ。`check` を再実行しない |
| 手元（人・エージェント） | 第 9.2 節で選んだ検査 | 全件は引き渡し前に**最大 1 回**、必要なときだけ |

🔴 **保存やコミットのたびに全件を自動起動するフックを置かない。** 選ばれていない検査は、
誰が起動しても同じだけ時間を使う。
