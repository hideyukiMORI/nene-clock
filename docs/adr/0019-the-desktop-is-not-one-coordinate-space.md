# ADR 0019 — デスクトップは 1 つの座標空間ではない。ドラッグは実ピクセルで計算する

- 状態: 受理
- 日付: 2026-09-22
- Issue: #95 / #96 / #100
- 影響する規則: ARC-003 / ARC-005 / CNF-004 / QLT-007 / QLT-012
- 関係: [ADR 0018](0018-the-window-knows-which-screen-it-is-on.md) を**置き換える**（前提が誤っていた）

## 文脈 — ADR 0018 は効かなかった。しかも前提が間違っていた

ADR 0018 は「窓は自分が載っている画面の変化を知り、そのとき大きさを決め直す」と決めた。
実装して実機で測ったところ、**症状は 1 つも直らなかった**。

診断ビルド（アプリの中から数字を書き出す枝）で分かったこと:

```text
moved  loc=(-293,958)  size=698x250   pref=582x208  gc=1953c10e  bounds=(0,0 3072x1728) scale=1.25
moved  loc=(-420,852)  size=1006x360  pref=582x208  gc=1953c10e  bounds=(0,0 3072x1728) scale=1.25
moved  loc=(-1044,780) size=2503x895  pref=582x208  gc=1953c10e  bounds=(0,0 3072x1728) scale=1.25
```

🔴 **`gc` が一度も変わらない。** 窓が別の画面へ深く入り込んでも、JDK は窓の
`GraphicsConfiguration` を差し替えない。**アプリには「画面が変わった」と気づく手段が無い。**
⇒ ADR 0018 の決定 1 と 3 は、実機では**一行も実行されていなかった**。

## 根本原因 — Java の仮想デスクトップは単位が混ざっている

診断ビルドに画面一覧を出させた（施主の 4 画面・実測）。

| 画面 | Java が報告する原点 | Java が報告する大きさ | 尺度 | 実際（Windows） |
| --- | --- | --- | --- | --- |
| 主 | **(0,0)** | 3072×1728 | 1.25 | (0,0) 3840×2160 @125% |
| 左 | **(-3840,0)** | 2560×1440 | 1.5 | (-3840,0) 3840×2160 @150% |
| 右 | **(3840,0)** | 2194×1234 | 1.75 | (3840,0) 3840×2160 @175% |
| 上 | **(3818,-1440)** | 1707×960 | 1.5 | (3818,-1440) 2560×1440 @150% |

🔑 **原点は実ピクセル、大きさは論理ピクセル。** 単位が混ざっている。

その帰結として、Java の座標空間には**どの画面にも属さない穴**が空く。
主モニタは 0〜3072 で終わり、左モニタは -3840 から -1280 までしかない。
**-1280 〜 0 は空白地帯**である。左へドラッグすると窓はまずここに入る（実測: 窓が -300 に居た）。

変換の規則そのものは実データで検算できる。

```text
実ピクセル = 原点 + (Java 座標 − 原点) × 尺度
窓:     Java -290  → 0 + (-290)×1.25       = -362  … 実測 -300 付近 ✓
ポインタ: Java -1284 → -3840 + (2556)×1.5   = -6    … 実測 -2 ✓
```

### そして、ポインタの座標源が 2 つあって食い違う

```text
ev=  1,1348   ptr=   1,1348   dev=\Display3   ← 同じ画面の上では一致する
ev= -2,1347   ptr=-1284,1123  dev=\Display0   ← 別の画面へ入った瞬間 1282px ずれる
```

- `MouseEvent#getXOnScreen()` … **イベント源（窓）が載っている画面**の尺度で返す
- `MouseInfo#getPointerInfo()` … **ポインタが載っている画面**の尺度で返す

ADR 0018 の実装は前者を使っていた。**座標源の選択が誤っていた。**

### 症状との対応（すべて実測・自動ドラッグで再現）

| 症状 | 実測 | 説明 |
| --- | --- | --- |
| 窓がポインタから 1500px 飛ぶ | 左へドラッグ: `cursor=-540` のとき `win=+1200` | 穴に入った窓の位置を、両者が別々の尺度で解釈する |
| 右へのドラッグは壊れない | 右（175%）へ: 727→1018 に一度だけ変わり、最後まで追従 | 正の側では窓が穴を跨いだまま次の画面に拾われる |
| 窓が ×1.2 ずつ膨らむ | 582→698→838→1006→… `pref` は 582 のまま | Windows が実寸を 1.5/1.25 倍に直すたび、JDK が**古い 1.25 で割り戻す** |
| DPI 設定を変えても飛びは消えない | `uiScale=1` / `dpiaware=false` / Windows の system DPI 互換、すべてで再現 | 原因は DPI の扱いではなく**座標空間そのもの** |
| 旧版（v0.2.5）も同じに飛ぶ | 同じ自動ドラッグで同じ挙動 | ADR 0018 の変更が入れた不具合ではない |

## 決定

**デスクトップが 1 つの連続した座標空間だという前提を捨てる。ドラッグの計算は実ピクセルで行う。**

1. ポインタは `MouseInfo#getPointerInfo()` から取る（`getXOnScreen()` を使わない）。
   ポインタが載っている画面の `GraphicsConfiguration` も同時に得られる
2. ポインタの Java 座標を、**その画面の**原点と尺度で**実ピクセル**へ変換する
3. 実ピクセルの世界で「掴んだ点がポインタの下に来る」窓の位置を決める
4. それを、**ポインタが載っている画面**の原点と尺度で Java 座標へ逆変換して
   `setLocation` に渡す。⇒ ピア（JDK）がこのあと必ず掛ける変換を**見越して打ち消す**

   ⚠️ **当初この 4 は「窓が載っていると Java が思っている画面」と書いていた。実機の試験で否定された**
   （下の「測定で選んだ」を見よ）。ドラッグ中、ポインタは常に窓の上にある。
   窓自身の `GraphicsConfiguration` は、ピアが既に別の画面の変換を掛けている瞬間にも
   古い画面を返し続けるので、**ピアの現実に近いのはポインタの画面のほうである**。
5. 窓の大きさが、設定から決まる大きさ（content pane の preferred size）と違っていたら**戻す**。
   ⇒ ×1.2 の膨らみは、画面の変化に気づけなくても潰れる

> ⚠️ **2026-09-22 追記（Issue #100・実機の自動ドラッグ試験台）— 決定 4 の「どの画面で逆変換するか」は反証された。**
> 左へのドラッグ step50 で、狙った実ピクセル -600 を窓の GC（主・1.25）で逆変換して `setLocation(-480)` を渡したところ、
> 窓は実ピクセル **+1200** に着いた。+1200 は **左画面の写像を -480 に掛けた値**（`-3840 + (-480+3840)×1.5`）である。
> ⇒ **ピアは既に左画面の写像を使っているのに、`getGraphicsConfiguration()` はまだ主画面を返している。**
> 窓の GC は「大きさの経路で古い」だけでなく、**ピア自身の `setLocation` 変換に対しても古い**。
> 決定 5（大きさの復元）と可逆性は実機で**確認された**（膨らまない・戻ると元の大きさに戻る）。
> 決定 1〜3（実ピクセルで計算する・ポインタは `MouseInfo` から取る）も維持する。**外れたのは 4 の鍵だけ**である。
> どの画面を鍵にするかは機械では決められないので、**`-Dneneclock.dragStrategy=window|pointer|delta` で選べる
> 一時的な分岐**（`DragStrategy`）を置き、実機の測定で選ぶ。選ばれたら残り 2 つは消し、本 ADR の決定 4 を書き直す。

🔑 **4 が肝である。** `setLocation` は必ず「窓の GC の尺度」で変換される。だから正しい Java 座標を
渡しても届かない。**渡すべきなのは、変換されたあとに正しくなる値**である。

`GraphicsEnvironment` は使わない（禁止のまま）。窓とポインタが、それぞれ自分の画面を答える。

## 測定で選んだ（2026-09-22・施主の実機・合成ドラッグ）

決定 4 の「どの画面で逆変換するか」は机上では決まらなかったので、**4 案を 1 つのビルドに入れて
実機で走らせ、数字で選んだ**（`-Dneneclock.dragStrategy` で切り替え・選定後に分岐は消した）。

主（125%）→ 左（150%）へ 70 歩ドラッグしたときの、掴み点とポインタの実ピクセル距離:

| 案 | 逆変換に使う画面 | 左へのドラッグ | 判定 |
| --- | --- | --- | --- |
| `window` | 窓の `GraphicsConfiguration` | **1842px 外れ、戻らない** | ❌ |
| **`pointer`** | **ポインタの画面** | **70 標本中 2 標本だけ外れ、直後に復帰** | ✅ **採用** |
| `delta` | 使わない（移動量だけ足す・跳びは捨てる） | 窓が動かない | ❌ |
| `verify` | ポインタの画面 ＋ ピアの置き直しを読み戻しで検出 | `pointer` と同着（2 標本） | ❌ |

右（125%→175%）はどの案でも追従した（ずれ 30px ＝標本の遅れの範囲）。

🔑 **`verify` が `pointer` に勝てなかったことが、残る欠陥の性質を示している。**
読み戻しで「ピアが置き直した」ことに気づくことはできるが、**気づいた時点でその 1 フレームは
既に起きている**。Java からは事後にしか触れない。⇒ 境界をまたぐ瞬間の 1〜2 フレーム（約 60ms）の
跳びは、この経路では消せない。**消せないことを、消したと書かない**（Issue #101）。

## 強制

- **active**: 変換は副作用の無い純関数に置き、`:ui:swing:test` が正例・反例を検証する（QLT-007）。
  画面の記述（原点・尺度）は値として渡すので、4 画面・混在尺度の状況を headless で再現できる
- 🔴 **不能**: 実機の挙動そのもの。WSLg に複数画面も per-monitor DPI も無い（QLT-012）。
  ただし**自動ドラッグの試験台がある**（`SendInput` で合成したドラッグ＋DPI 対応の測定プロセス）。
  合格条件を数値で決め、[quality/gate-proofs.md](../quality/gate-proofs.md) に残す

## 結果

- 掴んだ点がポインタの下に留まる（どの向きへ、どの尺度の画面へでも）
- 窓が膨らまない
- 🔴 代償: 窓の大きさは画面の拡大率に応じて**実寸では変わる**（125% で 727px、175% で 1018px）。
  これは Windows の拡大率設定に従った正しい挙動であり、本 ADR では変えない
- 🔴 **残る欠陥**: 画面の境界をまたぐ瞬間、窓が 1〜2 フレーム（約 60ms）だけ大きく跳んで、
  すぐ戻る。ピアが窓を置き直す一手であり、Java からは事後にしか気づけない（Issue #101）。
  **直ったのは「飛んだまま戻らない」であって、「一度も跳ねない」ではない。**
- 🔴 この計算は「原点は実ピクセル・大きさは論理ピクセル」という**観測された挙動**に依存する。
  JDK がこれを直したら、変換は恒等式に近づくだけで壊れはしないが、
  **前提が変わったことに気づけるよう、gate-proofs に実測値を残す**

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| ADR 0018 の方針（画面の変化を見て大きさを直す）を続ける | **実機で一行も実行されなかった。** JDK は窓の GC を更新しない |
| `getXOnScreen()` のまま補正する | 座標源そのものが「窓の画面」基準。ポインタが別の画面に居るとき、補正に必要な情報が入っていない |
| `-Dsun.java2d.uiScale=1` / DPI 非対応にする | 実測で**飛びは消えない**。しかも全画面で文字が小さくなる／ボケる |
| Windows の互換設定（system DPI aware）で配る | 実測で**飛びは消えない**。配布物の外側の設定に依存するのも筋が悪い |
| OS にドラッグさせる（ネイティブのタイトルバー相当） | 枠なし窓を捨てることになる（ADR 0008）。JNI 無しでは届かない |
| 画面をまたぐドラッグを禁止する | 施主の要件そのものを消す |
