# ADR 0016 — 検証は差分から選ぶ。ゲートは 1 つのまま、回す回数を決める

- 状態: 受理
- 日付: 2026-09-22
- Issue: #92
- 影響する規則: QLT-001 / QLT-005 / QLT-008 / QLT-010 / QLT-012 / QLT-013

## 文脈

完了の定義は `./gradlew check` **1 本**である（QLT-001 / QLT-005）。これは変えない。
問題はゲートの数ではなく、**同じ全件を何度回すか**が決まっていなかったことである。

書かれていた手順を並べると、1 つの変更に対して全件が最低 3 回走る形になっていた。

| どこ | 何を要求していたか | 回数 |
| --- | --- | --- |
| `docs/DEVELOPMENT_WORKFLOW.md` 第 2 節 9 | 「引き渡し前に `./gradlew check` を**完全に**回す」 | 手元で 1 回 |
| `docs/handoff/2026-09-04.md` 第 8 節 6 | 「**コミットごとに** `git worktree add` で切り出して `check` を回す」 | 手元でコミット数だけ（しかも**キャッシュの無い木**で） |
| `.github/workflows/ci.yml` | `pull_request` と `push: main` の両方で `./gradlew check` | CI で 2 回 |

どれも単体では筋が通っている。重ねた結果として、**変更の大きさと無関係に**時間が伸びていた。

実測（`gh run list` / 2026-09 の直近 20 回）:

| 種別 | 実時間 | 備考 |
| --- | --- | --- |
| PR の `quality`（キャッシュ有効） | 41〜101s | |
| PR の `quality`（キャッシュ不発） | 217〜258s | 同じ枝で 4 回走った PR もある（#88） |
| squash merge 後の `main` への push | 39〜73s | **PR で緑だった内容をもう一度** |
| 文書だけの変更（#90） | PR 41s ＋ main 39s | Java を 1 行も触っていない |

手元の実測（2026-09-22・`org.gradle.caching=true` / `configuration-cache=false`）:

| 回し方 | 実時間 | 内訳 |
| --- | --- | --- |
| `check`（暖まった木・変更あり） | 15.3s | 102 タスク中 17 実行・41 キャッシュ・44 up-to-date |
| `check`（直後にもう一度） | 1.66s | **1 実行**（`validateConformance` だけ）・101 up-to-date |
| `check`（`clean` 後） | 15.9s | |
| `check`（キャッシュ無し・全再実行＝冷えた作業木の目安） | 37.8s | 102 実行 |
| `:core:domain:test`（暖かい） | 1.11s | |
| `validateConformance` | 1.12s | |

🔑 **暖かい木で `check` を回し直しても 1.7 秒**である。つまり本当の代金は「全件」そのものではなく、
**キャッシュの無い木で回すこと**（`git worktree add` した木・CI の冷えたランナー）と、
**変更と無関係な検査を選んでしまうこと**である。だから本 ADR は `check` を分割せず、
**回す場所と回数**を決める。

⚠️ 実測でもう 1 つ分かったこと: `validateConformance` は
`upToDateWhen(false)` で**決して up-to-date にならない**（waiver の期限が今日の日付に依存するため）。
そして**文書だけの変更で落ちうる唯一の検査**でもある（CNF-005）。
実際、この ADR の草稿は QLT-013 を定義する前に CNF-005 で落ちた。
⇒ 「文書だけだから何も回さなくてよい」は**誤り**であり、規則 ID・waiver・モジュールグラフに
触れたなら `validateConformance` を回す — 1 秒である。

さらに、**選び方が書かれていない**ため「念のため全件」が既定になっていた。
これは本リポジトリの原則（一つの方法に固定し、人の記憶ではなく機械に守らせる）の逆で、
「何を確かめるか」を毎回その場の気分で決めている状態である。

## 決定

**ゲートは 1 つのまま（`./gradlew check`）、それを回す場面を「PR に対して CI が 1 回」に固定し、
開発中の検証は差分から選ぶ。**

1. **差分から選ぶ。**「この変更で何が壊れうるか」を説明できない検査は回さない
   （選び方の表は `docs/DEVELOPMENT_WORKFLOW.md` 第 9 節）
2. **成功は再利用する。** 同じ木（`git rev-parse HEAD^{tree}`）に対する成功した検証は、
   rebase・amend・squash・担当交代・レビュー・merge を理由に回し直さない
3. **全件は既定ではない。** 共通基盤（build-logic・Gradle 設定・`config/`・JDK・整形設定・
   モジュールグラフ）を触ったときのように、**限定した検査では影響を確認できない具体的な理由**が
   あるときだけ、対象と理由を 1 行書いてから回す
4. **無関係な失敗で止まらない。** 差分に起因する失敗は直す。無関係と判断できる既存の失敗は
   根拠とともに別 Issue にし、現在の作業をそこで止めない
5. **緑になるまで回さない。** 再実行で通ったことを「合格」として扱わない（QLT-012 と同じ理由）

## 強制

**不能**（対象が「何を確かめるか」という判断そのもの）。QLT-010 と同じ扱いにする。
新しい規則 QLT-013 として `docs/QUALITY_GATES.md` に定義し、強制欄には `不能` と書く。
`planned` とは書かない — 実装する予定の検査が存在しないからである（ADR 0001）。

担保は 2 つ。

- **手続き**: PR 本文の「検証」欄に、回したコマンドと**検証済みの木のハッシュ**を書く。
  回さなかった検査があるなら、なぜ不要かを 1 行で書く
- **機械（規則の強制ではない補助）**: Gradle の up-to-date 検査とビルドキャッシュが、
  入力の変わっていないタスクの再実行を実時間で無効化する。
  ⚠️ これは「同じ木なら結果が同じ」ことの保証であって、**選び方の強制ではない**

## 結果

得られるもの:

- 文書・コメント・PR 本文だけの変更で、Java のテストを 1 件も回さなくてよくなる
- 手元の全件が「引き渡し前の最後の 1 回」に減り、それすら差分が Gradle の入力に触っていなければ不要になる
- 「何を確かめるか」が表になったので、判断が人の記憶から離れる

失うもの:

- 🔴 **CI で初めて落ちることが増える。** これは受け入れる。手元と CI で同じ全件を 2 回回す代金より、
  CI が 1 回落ちて直す代金のほうが小さい（実測: CI の全件は 41〜258s）
- 🔴 差分の読み違いを人（エージェント）が直接引き受ける。読み違えたら CI が落ちる。
  **落ちたら全件に戻すのではなく、読み違えた理由を Issue に書く**

移行に必要な作業:

- `docs/DEVELOPMENT_WORKFLOW.md`（第 2 節の手順と新しい第 9 節）
- `docs/QUALITY_GATES.md`（QLT-013 の定義、冒頭の「唯一の完了定義」の言い方）
- `AGENTS.md` / `CLAUDE.md`（エージェントが最初に読むところ）
- `.github/workflows/ci.yml`（`push: main` の重複実行）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| CI から `check` を外す／必須ジョブを減らす | 施主の指示は「検証をすべて無効化する変更にはするな」。QLT-001 / QLT-010 を壊す。**速いのは検証を捨てたからではいけない** |
| 変更範囲からテストを自動選定する基盤（テスト影響解析）を作る | 施主が明示的に禁止（「大掛かりな自動選定基盤は作らない」）。Gradle のタスクパス指定と up-to-date で足りる。**検査を選ぶ機械を自作したら、その機械にも QLT-007 の正例・反例が要る** |
| 文書は変えず「気をつける」で運用する | 本リポジトリの原則の逆。人の記憶に置いた規則は、今回のように**重なっても誰も気づかない** |
| `check` を「速い check」と「遅い check」の 2 タスクに分ける | 第 2 の完了定義を作ることになる（QLT-001 違反）。**ゲートは 1 つ、回数を決めるのが本 ADR の立場である** |
| `push: main` の CI をそのまま残す | PR で緑だった同じ木をもう一度回している。ただし**キャッシュの種蒔き**という実効があるため、完全には消さず条件を付ける（第 9 節） |
