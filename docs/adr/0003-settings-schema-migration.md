# ADR 0003 — 設定スキーマの移行方針

- 状態: 受理
- 日付: 2026-09-03
- Issue: #22
- 影響する規則: ARC-002 / ARC-009 / ARC-010 / QLT-008

## 文脈

施主要件により、設定へ書体（FR-043）と文字色（FR-044）を追加する。
これは保存形式の変更であり、**すでに v1 で保存された設定が存在しうる**。

現在の実装は「対応外の版は `UNSUPPORTED_SCHEMA` を返して既定値へ落とす」だけを持つ。
このまま版を 2 に上げると、v1 で保存された時刻表記・秒表示・日付表示・最前面・サイズが
**利用者に何も告げずに消える**。ARC-009 が禁じているのはまさにその挙動である。

一方で「版を上げずにキーだけ足す」道もある。しかしそれを選ぶと、
「v1 が書いていないから欠けているキー」と「v2 なのに壊れているキー」を区別できなくなり、
FR-042 の `INVALID_VALUE` が意味を失う。

## 決定

**版を 2 に上げ、`[EARLIEST_MIGRATABLE, CURRENT]` の範囲に入る版は読み込み時に移行する。
未来の版は `UNSUPPORTED_SCHEMA` のままとする。**

- 移行は**保存形式を所有する `:adapters:preferences` が持つ**（ARC-002）。
  application / domain は「移行があったこと」を知らない
- 移行は**メモリ上で行い、`load()` は保存領域を書き換えない**。
  v2 として書き戻されるのは、利用者が次に設定を保存したときである
- 欠けている v2 のキーは domain の既定値で埋める。推測しない
- v1 に存在するキーが壊れていれば、移行の前に `INVALID_VALUE` を返す

## 強制

- **active**: v1 の保存値から移行できること、既存 5 項目が保たれること、
  未来の版が `UNSUPPORTED_SCHEMA` になることを単体テストで検証する（QLT-008）
- **planned**: 版が 3 以上に増えたときの「移行経路の網羅」検査。
  版が 2 つしか無い現在は、テストの列挙で足りる

## 結果

得られるもの:

- 利用者の設定が版上げで消えない
- 「読めない」と「古い」が型の上で別物として扱われる

失うもの:

- 版を上げるたびに移行と、そのテストを書く義務が発生する
- `PreferencesSettingsAdapter` が版ごとの読み取り経路を持つぶん大きくなる
  （JAV-012 の複雑度上限に当たったら、版ごとの読み取りを分ける）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 版を上げず v1 にキーを足す | 「旧版なので欠けている」と「壊れている」を区別できなくなり、FR-042 の `INVALID_VALUE` が意味を失う |
| v1 を `UNSUPPORTED_SCHEMA` として既定値へ落とす | 利用者の設定が黙って消える。ARC-009 が禁じる挙動そのもの |
| `load()` の中で v2 へ書き戻す | 読み取りが副作用を持つ。「読むだけ」のつもりの操作が保存領域を変えるのは、後から追えない事故になる |
| 移行を application 層に置く | 保存形式を知るのは adapter の責務。application が版を知ると、ポートの意味が「保存」から「Preferences の操作」へ落ちる（ARC-002） |
| 移行できない版を黙って既定値にする | 未来の版を推測して読むことになる。読めないものは読めないと返す |
