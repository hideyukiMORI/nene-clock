# ADR 0004 — 現在の設定の所有者を application に置く

- 状態: 受理
- 日付: 2026-09-03
- Issue: #24
- 影響する規則: ARC-004 / ARC-005 / ARC-011

## 文脈

設定を GUI から変更できるようにすると（FR-045）、**「いまどの設定を使っているか」を
誰かが持たなければならない**。M0 までは設定が変わらなかったので、起動時に読んだ値を
そのまま使い回すだけで済んでいた。

置き場所の候補は 3 つある。

1. `:ui:swing` の部品が持つ — ARC-004 が禁じる。保存される設定は UI の一時状態ではない
2. `:app`（合成ルート）が持つ — ARC-006 が禁じる。合成ルートに業務状態を置くと、
   配線とロジックの境目が消える
3. `:core:application` が持つ

3 が残る。しかし ARC-005 は「可変な状態を持ってよいのは `:ui:swing` の Swing 部品の内部だけ」
と書いており、そのままでは 3 も書けない。**規則と要件が正面から衝突している。**

## 決定

**ARC-005 を改訂し、可変な隔離区画を 2 つにする。** 追加するのは
`:core:application` の `SettingsHandler` ただ 1 つで、そこが可変に持てるのは
「現在の `UserSettings` を指す参照」だけである。

- 値そのものは不変（`UserSettings` は `record`）
- 参照の差し替えは `apply(UserSettings)` ただ 1 本
- 読むのは `current()` だけで、返るのは不変な値
- 保存に失敗しても現在値は差し替える。利用者の操作を無かったことにするより、
  「表示は変わったが保存できなかった」と伝えるほうが正直である（FR-045）

ARC-004 の状態表にも所有者としてこの型を書く。

## 強制

- **active**: ArchUnit が `:core:domain` のフィールドをすべて `final` に強制する
- **active**: ArchUnit が `:core:application` のフィールドを、`SettingsHandler` を除いて
  すべて `final` に強制する。**隔離区画の名前が規則の中に書いてある**ので、
  2 つ目の可変な場所を作ると検査が落ちる
- **不能**: 「参照の差し替えが `apply` 経由だけか」の静的検査。フィールドが private で
  setter が無いことをもって担保する

## 結果

得られるもの:

- 設定を変えられる要件を満たしつつ、可変な場所が数えられる状態を保てる
- UI と合成ルートは状態を持たないままでいられる

失うもの:

- ARC-005 の「可変なのは UI だけ」という一文の単純さ。区画が 1 つ増えた
- 区画が増えるたびに ArchUnit の除外リストが伸びる。3 つ目を足すときは、
  本当に必要かをこの ADR と同じ形で問い直す

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| UI の部品が現在の設定を持つ | ARC-004。保存される設定は UI の一時状態ではない。タブが増えるたびに同じ事実が二重化する |
| 合成ルート（`:app`）が持つ | ARC-006。配線しかしないはずの場所に業務状態が入り、境目が消える |
| 変更のたびに保存領域から読み直す | 読み取りが失敗したとき、直前に利用者が入れた値を失う。保存の失敗と表示の失敗が同じ事故になる |
| `SettingsHandler` を不変にして毎回作り直す | 作り直した新しいインスタンスを誰かが持つ必要があり、可変な場所が UI か合成ルートへ移動するだけ。問題が消えていない |
| 保存に失敗したら現在値を元へ戻す | 利用者の操作が理由の説明なく巻き戻る。失敗は伝えるべきであって、隠して戻すべきではない |
