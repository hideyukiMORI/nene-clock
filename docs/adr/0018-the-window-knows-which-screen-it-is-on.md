# ADR 0018 — 窓は自分が載っている画面の変化を知る。ドラッグは画面座標で決める

- 状態: 受理
- 日付: 2026-09-22
- Issue: #95 / #96
- 影響する規則: ARC-003 / ARC-005 / CNF-004 / QLT-012 / SWG-004
- 関係: [ADR 0008](0008-the-window-is-the-clock.md) を補う（窓の大きさは設定に従う、をいつ守るかを決める）。
  [ADR 0006](0006-typefaces-are-bundled-not-discovered.md) / [ADR 0011](0011-transparency-is-asked-for-not-assumed.md)
  の「実行環境を読まない」との線引きを本 ADR で決める

## 文脈 — 実測（2026-09-22・施主の Windows 実機・MSI v0.2.5）

施主報告: ①拡大率の違うモニタへドラッグすると窓が勝手に大きくなる ②ドラッグ中に画面をまたぐと
窓がポインタから大きく外れて遠くへ行く。

### 環境（per-monitor 対応で測り直した実値）

| モニタ | 実解像度 | 拡大率 |
| --- | --- | --- |
| DISPLAY4（主） | 3840×2160 | **125%** |
| DISPLAY1 | 3840×2160 | **150%** |
| DISPLAY2 | 3840×2160 | **175%** |
| DISPLAY3 | 2560×1440 | **150%** |

⚠️ 最初の測定は「全部 96dpi（100%）」に見えた。**測定していたプロセス自身が DPI 非対応だったため**である。
測る側の DPI 認識を宣言していない測定値は、モニタの拡大率について何も言っていない。

同梱ランチャ `NeNe Clock.exe` の埋め込みマニフェストは per-monitor 対応を**宣言している**:
`dpiAware = true/PM` / `dpiAwareness = PerMonitorV2, PerMonitor, system`。
一方 `NeNe Clock.cfg` の `java-options` は `-Djpackage.app-version` のみで、DPI の指定は無い。

### 決め手になった実測 — 外から動かす分には、何も壊れていない

`SetWindowPos` で窓を動かし、per-monitor 対応の測定プロセスで矩形を読んだ。

| 置いた画面 | 拡大率 | 実ピクセル | 論理サイズ |
| --- | --- | --- | --- |
| DISPLAY4 | 125% | 956×260 | **765×208** |
| DISPLAY1 | 150% | 1147×312 | **765×208** |
| DISPLAY2 | 175% | 1338×364 | **765×208** |
| DISPLAY4（戻り） | 125% | 956×260 | **765×208** |

125%↔150% を 3 往復させても、毎回ぴったり同じ値に戻る。境界へ 80px 刻みで**這わせて**またがせても同じ。

🔑 **瞬間移動でも段階移動でも、JDK の DPI 処理は正しく、完全に可逆である。膨らまない。**
それでも施主が手でドラッグすると **7.43 倍（956×260 → 5642×1546）** まで膨らむ。
⇒ **差は 1 つしかない。ドラッグ中だけ、アプリが毎イベント `frame.setLocation(...)` を呼んでいる。**

### 過渡状態が写っていた

境界を這わせたときの 2 サンプル:

```text
x=-400   956x260  scale=125%  logical=765x208
x=-480   956x260  scale=150%  logical=637x173   ← 画面は新しい尺度。窓の寸法はまだ古い
x=-640  1147x312  scale=150%  logical=765x208   ← ここで作り直された
```

**数百ミリ秒のあいだ、窓は「新しい画面に居るのに、古い寸法のまま」になる。**
この間、`frame.getLocation()` は新しい尺度で返り、`event.getX()`（content pane 相対）は古い寸法の窓の中の座標である。

現在のドラッグ（`ui/swing/.../ClockWindow.java:158-165`）はこの 2 つを足している。

```java
Point where = frame.getLocation();
frame.setLocation(where.x + event.getX() - origin.x, where.y + event.getY() - origin.y);
```

- **尺度の違う数を足している**（過渡状態のあいだ）
- **相対累積なので、一度ずれると戻らない**（毎イベント誤差が足し込まれる）
- そして、その `setLocation` 自体が過渡状態のさなかに窓を動かすので、作り直しが再発火する

⇒ ②（遠くへ外れる）も ①（膨らむ）も、**同じ 1 つの根**から出ている。

## 決定

**窓は、自分が載っている画面が変わったことを知り、そのとき設定から大きさを決め直す。
ドラッグは画面座標での絶対位置決めにし、過渡状態では動かさずに掴み点を取り直す。**

1. `componentMoved` で `getGraphicsConfiguration()` を見る。変わっていたら `fitToClock()` と
   角丸の適用をやり直す。⇒ 何が起きたあとでも、窓の大きさは**必ず設定どおりに戻る**
2. ドラッグは「ポインタの画面座標 − 掴み点」で**毎回決め直す**。前の位置に足し込まない。
   ⇒ ずれても次のイベントで自己修正する
3. 画面が変わった直後のイベントでは窓を動かさず、**掴み点を取り直す**（尺度が混ざる区間を避ける）

### ADR 0008 との関係

ADR 0008 は「窓の大きさは設定に従う」と決めた。**その約束は、いままで設定を変えた瞬間にしか
守られていなかった。** 本 ADR は、それを「画面が変わったときにも守る」へ広げる。新しい規則ではなく、
既存の規則を守る場所を増やす変更である。

### 「実行環境を読まない」との線引き（ADR 0006 / 0011）

ADR 0006 と 0011 は `GraphicsEnvironment` を禁じた。禁じた理由は
**「環境に何があるかを一覧で問い合わせて、それに応じて振る舞いを変える」**ことだった
（書体が有るか無いか・半透明が使えるか）。

本 ADR が読むのは `window.getGraphicsConfiguration()`、すなわち **この窓がいまどこに居るか**という
窓自身の属性である。環境の品揃えを尋ねてはいない。

- **`GraphicsEnvironment#getLocalGraphicsEnvironment()` の禁止は維持する**（`config/forbiddenapis/platform.txt` を変えない）
- 画面の一覧を取りに行かない。**窓が自分について答えられることだけを読む**

## 強制

- **active**: forbidden-apis は `GraphicsEnvironment` を禁じたまま。今回の実装はこれを使わない
- **active（部分）**: ドラッグの座標計算を副作用のない関数に切り出し、`:ui:swing:test` で
  「掴み点がポインタの下に留まる」「窓の大きさが途中で変わっても掴み点が窓の外へ出ない」を検証する
- 🔴 **不能**: 複数モニタ・per-monitor DPI の挙動そのものは機械検査できない。
  **WSLg には per-monitor DPI が無いので、この修正は WSLg では検証できない**（QLT-012）。
  検証は「MSI を作り直して実機に入れ、本 ADR と同じ測定をやり直す」であり、
  数字を [quality/gate-proofs.md](../quality/gate-proofs.md) に残す。
  **測る側の DPI 認識を宣言していない測定値は証拠として使わない**

## 結果

- 画面をまたいでも、窓の大きさは設定どおりに戻る（膨らみが累積しない）
- 掴んだ点がポインタから外れない。外れても次のイベントで戻る
- 🔴 代償: 窓の大きさは画面の拡大率に応じて**物理的には変わる**（125% の画面で 956px、175% の画面で 1338px）。
  これは Windows の拡大率設定に従った正しい挙動であり、本 ADR では変えない。
  「どの画面でも同じ物理サイズに見せる」は別の要求であり、必要になったら別 ADR で問い直す
- 🔴 代償: 窓の位置は依然として保存されない。再起動すると既定の画面の中央に戻る（別件）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| `-Dsun.java2d.uiScale=1` や DPI 非対応マニフェストで per-monitor をやめる | 高 DPI の画面で**文字がボケる**。時計の中身は文字しかない。ADR 0008 の「静かな塊」が成立しない |
| JDK 側の不具合として報告し、待つ | 実測で JDK は正しい。**外から動かす分には完全に可逆**である。壊しているのはこちらのドラッグ実装 |
| ドラッグ中だけ DPI 変更を無視する（窓を強制的に元の寸法に固定する） | OS と綱引きになる。マニフェストで「面倒を見る」と宣言しておきながら見ない、という現在の状態の別形である |
| 画面ごとの拡大率を読んで、こちらで文字サイズを補正する | 利用者が選んだ文字サイズを黙って書き換えることになる（ADR 0017 で却下したのと同じ筋） |
| `GraphicsEnvironment` から画面の一覧を取る | ADR 0006 / 0011 で閉じた経路。**窓自身に尋ねれば足りる** |
