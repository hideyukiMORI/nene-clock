# ADR 0022 — 配布物は 1 回だけ作る。GitHub Release は作り直さず、Store に出した実行の成果物をそのまま出す

- 状態: 受理
- 日付: 2026-10-04
- Issue: #132
- 影響する規則: QLT-001 / QLT-005 / ADR 0013（決定 7）/ ADR 0020

## 文脈

ADR 0013 の決定 7 は「`v*` タグを打つと、配布物が自動で GitHub Release に添付される」だった。
タグで `Release` ワークフローが起動し、その場で MSI・zip・`.deb` を**作って**添付する。

ADR 0020 で Store を足し、タグは Store の認定が出てから打つことにした（DEVELOPMENT_WORKFLOW 第 10 節）。
すると、Store に出す MSIX を作る実行と、タグで MSI・zip を作る実行が別になる。同じ commit でも、**2 回作ったものが
バイト単位で同じとは限らない**（再現するかは確かめていない。MSI にはビルドの時刻が入る）。
「Store の 1.0.0」と「GitHub の 1.0.0」の中身が違いうる状態になる。

NeNe Loupe は、提出のときに作った ZIP を控えておき、認定のあとにそれをそのまま公開している。
施主の判断（2026-10-04）: Clock も揃える。

## 決定

**配布物は 1 回だけ作る。GitHub Release には、Store に出した MSIX を作った実行の成果物を、作り直さずに添付する。**

1. `Release` ワークフローは**タグでは起動しない**。タグは、公開のときにワークフローが打つ
2. 手動の起動で実行の ID（`publish_from_run`）を渡すと、`release` ジョブがその実行の成果物を取ってきて、
   その実行の commit に `v<version>` のタグを打ち、GitHub Release に MSI・zip・`.deb` を添付する。**何も作らない**
3. 出す前に確かめる: その実行がこのワークフローの成功した実行であること・commit が main に載っていること・
   作ったときの `.sha256` と中身が一致すること・提出できる MSIX（`NeNe-Clock-store.msix`）がその実行にあること・同じタグの Release がまだ無いこと
4. 既定は試し実行（`dry_run: true`）。確かめるだけで、タグも Release も作らない。公開するときだけ `false` を選ぶ
5. 版は、その commit の `gradle.properties` から読む（版の入力は 1 か所のまま）

## 強制

- **active**: `release` ジョブの検査（決定 3）。満たさなければ公開の前に落ちる
- **active（実測・2026-10-04）**: 試し実行で、通る側と、main に載っていない実行で落ちる側を測った（gate-proofs 第 28 節）。
  本当の公開は、Store の認定が出るまで試していない
- **不能**: 「Store に出した MSIX が、渡した実行のものであること」。Partner Center に何を上げたかはワークフローから見えない。
  提出のときに、実行の ID と MSIX の SHA-256 を `docs/release/store-listing.md` に控えることで人が担保する

## 結果

得られるもの:

- Store の MSIX と、GitHub の MSI・zip が同じ app-image から出たものになる（`packageMsix` が app-image の全ファイルを突き合わせている）
- 「タグを打ったら何かが作られる」という、見えない 2 回目のビルドが無くなる

失うもの・変わるもの:

- **`git tag` を手で打って push しても、何も起きなくなる。** 公開は必ずワークフローの手動の起動から行う
- 成果物の保存期間（GitHub の既定は 90 日）を過ぎた実行は出せない。認定が長引いたら、作り直して提出からやり直す
- 公開の手順が 1 つ増える（実行の ID を控える）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| いまのまま、タグで作り直す | Store と GitHub で同じ版の中身が違いうる |
| ビルドをバイト単位で再現できるようにする | できれば最良だが、jpackage の MSI と jlink の実行環境の再現性を確かめる必要があり、範囲が大きい。作り直さなければ、再現性に頼らずに済む |
| 提出のときに成果物を手元へ控えておき、手で Release に上げる | 人の手と手元の置き場に頼る。実行の成果物は GitHub が持っている |
| タグを手で打ち、タグで起動したジョブが「同じ commit の成功した実行」を自分で探して出す | 同じ commit に実行が複数あると、どれが提出したものかをワークフローは知らない。ID を人が渡すほうが取り違えない |
