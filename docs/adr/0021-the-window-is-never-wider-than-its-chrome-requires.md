# ADR 0021 — 窓の下限は「クロームが収まる大きさ」だけにする。固定の 320×160 をやめる

- 状態: 受理
- 日付: 2026-10-04
- Issue: #97
- 影響する規則: FR-030 / FR-047 / FR-049 / ADR 0008 / ADR 0017

## 文脈

窓の下限は 320×160 の固定だった。タブと OS のタイトルバーがあった頃の値である（ADR 0008 でどちらも消えた）。

ADR 0017 で余白を設定にしたとき、**小さい設定では余白の設定が効かない区間がある**ことが実測で分かった（Issue #97）。
自然な大きさが下限を下回ると、余白をいくら増やしても窓は 320×160 のまま動かない。
利用者からは「余白の帯の左側が無反応」に見え、窓の中に頼んでいない空白が残る。

これは端の事例ではなかった。**施主が常用している設定（Anton 56pt・24 時間・秒あり・日付あり・余白 8）がこの区間に入っていた。**
2026-10-04 に実機の窓を測ると 320×160 で、同じ設定の自然な大きさは 212×133 である。
つまり施主の時計は、設定した余白 8 ではなく、左右に 54px ずつの余白で描かれていた。

施主の判断（2026-10-04）: 1.0.0 の前に直す。

## 決定

**窓の下限を、操作用のクローム（設定と終了のボタン）が四方の余白ごと収まる大きさにする。それ以外の理由で窓を広げない。**

- 下限は固定の数字で持たず、クロームの寸法から求める（`ClockWindow.smallestSize`）。ボタンが増えても下限は付いてくる
- 下限は広げる向きにしか効かない（変わらない）。文字が切れることはない
- 初期の大きさ（480×240）は、設定が反映される前の一瞬の値であり、触らない

## 強制

- **active（実測）**: gate-proofs 第 27 節。7 通りの設定で窓の大きさを測り、余白を変えると窓が動くことを確かめた
- **planned**: 窓の大きさを自動テストで固定すること。`ClockWindow` は実際の窓を作るので、ヘッドレスの単体テストが無い
  （UI 層のテストは QLT-009 の planned と同じ扱い）

## 結果

得られるもの:

- 余白の設定がほぼ全区間で効く。窓は中身ちょうどになる（「窓そのものが時計」— ADR 0008）
- 下限に根拠がある（ボタンが押せなくならない大きさ）

失うもの・変わるもの:

- 🔴 **小さい設定を使っている人の窓は、版を上げた瞬間に小さくなる。** 施主の設定では 320×160 → 212×133。
  これは「頼んだ余白のとおりになる」変化だが、見た目は変わる。前の見た目に戻すには余白を増やす
- 文字も余白も最小（24pt・余白 8・秒なし・日付なし）にすると、窓は 92×58 になる。掴む面積は小さい。
  それでもクロームは収まるので、設定を開いて戻せる

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 下限を無くす | クロームより小さい窓を作れてしまう。ボタンがはみ出して、設定を開けなくなる |
| 320×160 のままにする | 設定が効かない区間が残る。施主の常用の設定がその区間にある |
| 下限を別の固定の数字（たとえば 120×60）にする | 根拠の無い数字が残る。クロームの寸法が変わったときに付いてこない |
| 小さくなる人のために、移行で余白を増やして見た目を保つ | 「頼んでいない余白を、頼んだことにする」ことになる。保存形式の版も上がる。見た目が変わることは ADR とリリースの説明に書く |
| 窓の手動リサイズを足す | ADR 0008 で却下済み |
