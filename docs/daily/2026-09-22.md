## 1. 検証を差分から選ぶ（#92 / ADR 0016）

施主の指示は「無関係な検証の反復で開発が遅い」。調べると、**ゲートが 1 つであること**と
**同じ全件を何度も回すこと**が混ざっていた。

| どこ | 何を要求していたか |
| --- | --- |
| DEVELOPMENT_WORKFLOW 第 2 節 9 | 「引き渡し前に `check` を**完全に**回す」 |
| handoff 2026-09-04 第 8 節 6 | 「**コミットごとに** worktree を切って `check` を回す」 |
| ci.yml | `pull_request` と `push: main` の両方 |

実測して分かったのは、**暖まった木の `check` は 1.66 秒**（102 タスク中 101 が up-to-date、
実行されるのは `validateConformance` だけ）だということ。冷えた木では 37.8 秒。
⇒ **代金は「全件」そのものではなく、キャッシュの無い木で回すことと、無関係な検査を選ぶことだった。**

だから `check` は分割せず（第 2 の完了定義を作らない・QLT-001）、**回す場所と回数**を決めた。
QLT-013 の強制欄は `不能` と書いた。判断そのものは機械で守れない。`planned` と書かなかった。

## 2. 余白と「いまの設定で起こりうる最大」（#94 / ADR 0017）

施主要件は「窓の大きさを変えられない」。**窓サイズを設定にしなかった。**
文字サイズと窓サイズの両方が大きさを主張すると、どちらかが必ず折れる
（＝時刻が切れる／文字が勝手に縮む）。余白なら、どちらも折れない。

作業中にもう 1 つ見つけた。幅の基準が **`"00:00:00 AM"` 固定**で、
**24 時間表記でも、秒を隠しても、AM/PM 分の幅が常に確保されていた。**

| 設定 | 窓の画素（WSLg 実測） |
| --- | --- |
| 24 時間・秒あり・日付あり・余白 30 | 388×250 |
| 同上・余白 160 | 648×510 |
| 同上・余白 8 | 344×206 |
| 12 時間・秒あり・日付あり・余白 8 | 483×206 |

⇒ 24 時間と 12 時間の差は **139px**。施主の実機（Windows）では **956 → 727px** に縮んだ。

継ぎ目の置き方: 「何を測れば最大になるか」は文字列の組み立てを知っている `ClockFaceQuery` が決め、
「測る」のは書体の送り幅を知っている `:ui:swing` がやる。**UI に `WIDEST_TIME` を持たせない**
（持たせた瞬間、整形の知識が 2 か所になる）。

## 3. 🔴 複数モニタ — 見立てを 2 回間違えた

### 3.1 まず環境を測った（そして測定器が嘘をついた）

施主の報告は「モニタを移すと窓が大きくなる」「ドラッグでまたぐと窓がポインタから遠く離れる」。

最初に PowerShell でモニタを列挙したら **全モニタが 96dpi（100%）**に見えた。
⚠️ **測定していたプロセス自身が DPI 非対応だったため**である。解像度から逆算して気づき、
`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` を宣言して測り直した。

| 画面 | 実解像度 | 拡大率 |
| --- | --- | --- |
| 主 | 3840×2160 | 125% |
| 左 | 3840×2160 | 150% |
| 右 | 3840×2160 | 175% |
| 上 | 2560×1440 | 150% |

🔑 **測る側の素性を宣言していない測定値は、測った対象について何も言っていない。**

### 3.2 外から動かす分には、何も壊れていなかった

`SetWindowPos` で窓を動かすと、瞬間移動でも 80px ずつの段階移動でも、
論理サイズ 765×208 は保たれ、3 往復しても 1px も狂わなかった。
**壊れるのは施主が手でドラッグしたときだけ**だった。

実測トレース（ドラッグ中・20 標本/秒）:

```text
    31ms   4929×1342   DISPLAY4(125%)
 16422ms   5914×1611   DISPLAY4(125%)   ← ×1.2
 16484ms   7096×1933   DISPLAY4(125%)   ← ×1.2
 16733ms   8515×2319   DISPLAY4(125%)   ← ×1.2
 17168ms  10218×2782   DISPLAY1(150%)   ← ×1.2
 17228ms   8515×2319   DISPLAY4(125%)   ← ÷1.2
```

係数は毎回きっかり **1.2 = 150% ÷ 125%**。掛け算の回数が割り算を上回るので際限なく膨らむ。
実測で **7.43 倍（956×260 → 5642×1546）**まで行った。

### 3.3 一度目の間違い — ADR 0018

ここから「窓は自分が載っている画面の変化を知り、そのとき大きさを決め直す」と決めた（ADR 0018）。
実装して PR #99 でマージし、MSI を作って実機に入れて測った。

🔴 **症状は 1 つも直らなかった。**

アプリの中から数字を書き出す診断ビルドを作って、理由が分かった。

```text
moved  loc=(-1044,780) size=2503x895  pref=582x208  gc=1953c10e  bounds=(0,0 3072x1728) scale=1.25
```

**`gc` が最後まで一度も変わらない。** 窓が別の画面へ深く入り込んでも、JDK は窓の
`GraphicsConfiguration` を差し替えない。⇒ ADR 0018 の決定は**実機で一行も実行されていなかった**。

### 3.4 根本原因 — Java のデスクトップは単位が混ざっている

診断ビルドに画面一覧を出させた。

| 画面 | Java の原点 | Java の大きさ | 尺度 |
| --- | --- | --- | --- |
| 主 | **(0,0)** | 3072×1728 | 1.25 |
| 左 | **(-3840,0)** | 2560×1440 | 1.5 |

🔑 **原点は実ピクセル、大きさは論理ピクセル。** だから Java の座標空間には
**-1280〜0 というどの画面にも属さない穴**が空く。左へドラッグすると窓はまずここに入る。

さらに座標源が 2 つあって食い違っていた。

```text
ev=  1,1348   ptr=   1,1348   dev=\Display3   ← 同じ画面の上では一致
ev= -2,1347   ptr=-1284,1123  dev=\Display0   ← 別の画面へ入った瞬間 1282px ずれる
```

`MouseEvent#getXOnScreen()` は**窓の画面**の尺度、`MouseInfo#getPointerInfo()` は
**ポインタの画面**の尺度で返す。ADR 0018 の実装は前者を使っていた。

### 3.5 二度目の間違い — ADR 0019 の決定 4

ADR 0019 を書き、「ドラッグは実ピクセルで計算し、**窓の画面**の変換を見越して打ち消す」と決めた。
実装して測ったら、**膨らみは止まったが、飛びは残った**（1842px）。

逆算したら 1px 単位で合った。

```text
狙った実ピクセル -600 → 窓の画面(0, 1.25) で逆変換 → setLocation(-480)
ピアが実際に置いた場所 → +1200 = 左画面(-3840, 1.5) の変換をそのまま掛けた値
```

**`getGraphicsConfiguration()` は、ピア自身の `setLocation` 変換に対しても古かった。**

### 3.6 決め方を変えた — 4 案を入れて測定に選ばせた

どの画面を信じるべきかは机上では決まらない。だから **4 案を 1 つのビルドに入れ**、
`SendInput` で合成したドラッグを実機で走らせて数字で選んだ。

| 案 | 逆変換に使う画面 | 左へのドラッグ | 判定 |
| --- | --- | --- | --- |
| `window` | 窓の GC | 1842px 外れ、戻らない | ❌ |
| **`pointer`** | **ポインタの画面** | **70 標本中 2 標本だけ外れ、直後に復帰** | ✅ |
| `delta` | 使わない（移動量だけ） | 窓が動かない | ❌ |
| `verify` | ポインタの画面＋読み戻しで検出 | `pointer` と同着 | ❌ |

選んだので分岐は消した（ARC-001）。

🔑 **`verify` が勝てなかったことが、残る欠陥の性質を示している。**
「ピアが置き直した」ことに気づくことはできるが、**気づいた時点でその 1 フレームは既に起きている。**

## 5. 判断の要点

- **効かなかったら、見立てを疑う番である。** ADR 0012 の教訓（2026-09-04）が、今日 2 回当たった。
  1 回目は前提（窓は画面を知っている）、2 回目は鍵（どの画面を信じるか）
- **決め打ちしないための分岐は、決まったら消す。** 4 案は測定のための一時的な状態であり、
  残せば ARC-001 違反になる
- **実装に予測を書かせてから測る。** 実装リナに「試験台が何を出すはずか」を先に書かせた。
  外れたことが分かったので、理解していない何かが残っていると判断できた
- **消せないものを消したと書かない。** 直ったのは「飛んだまま戻らない」であって
  「一度も跳ねない」ではない（#101）

## 6. 試験の道具が嘘をついた 2 件

1. **DPI 非対応のプロセスで測ると、全モニタが 100% に見える**（3.1）
2. **画面がロックされていると、合成クリックはロック画面に吸われる。** 窓は動かず、
   試験は「成立していない」のに数字だけは出る。⇒ 押下点に本当に対象の窓が居るかを
   `WindowFromPoint` で確かめてから始める形にした

どちらも「緑／赤」ではなく**測定が成立していない**状態であり、気づかなければ
そのまま結論にしていた。
